# BUG-009 — Conversational Approval Does Not Approve the Generated Design

**Repository:** architectural-intelligence + archisimple  
**Status:** Findings / Investigation  
**Priority:** High  
**Related:** BUG-008, ADR-AI-0002, ADR-AI-0004, Sprint 037.0, Sprint 037.1

---

## 1. Problem

A conversational design session can successfully progress through:

Brief → Space Programme → Layout → Geometry → Geometry Specification

and explicitly ask the user to approve the resulting buildable specification.

However, when the user answers:

> approved

the subsequent build action reports:

> There is no approved design to build yet. The design pipeline has to reach an approved Geometry Specification first.

The observed conversation therefore contains an apparent approval from the user, but the authoritative project state does not contain an approved Geometry Specification.

This prevents the already-implemented realisation path from being reached.

---

## 2. Reproduction

Use the following scenario:

1. Ask:

   > Build me a 100m² apartment.

2. Provide:
   - 2 bedrooms
   - 2 bathrooms

3. Allow the assistant to generate:
   - Architectural Brief
   - Space Programme
   - Layout
   - Geometry
   - Geometry Specification

4. When the assistant asks:

   > Please review the design and let me know if you approve it to be built.

   answer:

   > approved

5. Ask:

   > Build it.

### Observed

The host reports that there is no approved design / Geometry Specification.

### Expected

The conversational approval should result in the **existing approval mechanism** being invoked for the current generated Geometry Specification.

The project should then contain an authoritative approved Specification that can subsequently be consumed by the existing realisation path.

---

## 3. Important architectural boundary

This bug MUST NOT introduce a second approval mechanism.

Approval ownership remains with the host.

The conversational layer may:

- recognise approval intent;
- identify that the user is approving the current generated design;
- create an approval proposal/intent using the existing contribution boundary.

The host remains responsible for:

- resolving the authoritative artefact;
- validating that it is still current;
- approving it;
- persisting the approval state.

The model MUST NOT invent or trust an artefact identity supplied in conversational text when the current project state can provide the authoritative identity.

---

## 4. Investigation questions

Determine:

1. How is `"approved"` currently classified by `architectural-intelligence`?
2. Does an approval lane already exist?
3. Does an approval proposal already exist?
4. Is the existing `ArtefactApprovalSink` reachable from conversational interpretation?
5. If approval intent is recognised, why does the host not approve the current Geometry Specification?
6. How does the conversational layer identify the artefact being approved?
7. Can approval be safely bound to the current generated/approved candidate without accepting an identity invented by the model?
8. What happens if:
   - no Geometry Specification exists;
   - the Specification is already approved;
   - the Specification has been superseded;
   - the user says "approve it";
   - the user says "approved";
   - the user says "yes, build it";
   - the user approves an older conversational artefact after regeneration?

---

## 5. Existing architecture to preserve

The investigation MUST reuse existing approval infrastructure where possible.

Do not:

- create a new approval Request unless the existing architecture proves one is required;
- duplicate the host approval guard;
- make the AI directly mutate project state;
- allow the model to choose an arbitrary Specification ID/revision;
- combine approval and realisation into one operation;
- modify the realisation path merely to compensate for missing approval.

BUG-008 is considered closed: realisation correctly refuses when no approved Specification exists.
